# v0.11.0 review: BAM-9 live camera (cb10001)

An independent review agent probed 127.0.0.1 fakes only, using fuzzing and targeted cases. It found 3 high, 3 medium and 4 low/low-medium issues. All are fixed, with regression tests in `test/camera-review.test.js` ("#N"). The full suite passes 206/206, and the browser end-to-end check against a fake camera still plays.

It found no access-code exposure. The code is only sent after the CA + CN == serial check. Paths are authorized correctly, and the fMP4 box layout and durations are correct.

| # | Sev | Finding | Fix |
|---|-----|---------|-----|
| 1 | High | Revoked or expired session mid-stream + slow reader → `res.end()` without unsubscribing → `ERR_STREAM_WRITE_AFTER_END` **crashed the process** | A single `finish()` path: unsubscribe, stop the re-check, end. Writes are skipped once the response has ended or been destroyed |
| 2 | High | Negative or non-numeric RTSP `Content-Length` → endless loop in the parser (event loop hang) | `Content-Length` must be digits and ≤ 64 KB, headers ≤ 64 KB, the status line must be RTSP; otherwise protocol error and stop |
| 3 | High | SPS shorter than 4 bytes → `TypeError` thrown out of the TLS data handler → crash | Short SPS / empty PPS are ignored; `avcConfig` validates; every parser runs inside `safeData` (error + stop) |
| 4 | Med-High | Corrupt SPS → `parseSps` read zeros past the end, so a loop ran ~4e9 times | Bounds-checked reads, Exp-Golomb and loop caps, dimensions limited to 1–8192; the route ends that viewer on a bad config |
| 5 | Med | Replacing a hub (address/code change) froze its viewers and let the viewer cap be exceeded | `close()` sends `end` to the viewers and clears them; the route ends those responses |
| 6 | Med | After a reconnect the fMP4 timeline restarted at 0, freezing MSE playback | `Fmp4Writer.config()` keeps decode time and sequence counting up across re-inits |
| 7 | Med | An SPS/PPS change mid-stream never reached the decoder | A changed SPS/PPS is re-announced (new init segment) at the next keyframe; the hub resets its GOP |
| 8 | Low-Med | Quadratic `Buffer.concat` while buffering (26 s CPU for 32 MB) | `ByteQueue` copies only what a parser takes (3 MB frame in 16 KB reads: well under 1.5 s) |
| 9 | Low | Unbounded FU-A or access-unit accumulation | Capped at 4 MB, then dropped until the next access unit |
| 10 | Low | The code import could switch a cloud printer with a saved host but a cleared code to LAN, and refilled codes on removed printers | `importCloudAccessCode`: cloud-sourced only, never refills a deliberately cleared code on a printer with a host, skips removed rows |

Fixed from the plausible list:
- Closing the MJPEG view no longer opens a new stream (the error handler ignores the close).
- The GOP replay stops at the cap rather than keeping a GOP with holes.
- An MSE `QuotaExceededError` keeps the chunk and frees space.
- Server-to-client RTSP requests are treated as a protocol error.

Open: the initial ~2 s start-up stall in the headless end-to-end check (with an I_PCM test stream) recovers on its own. Re-check it on real hardware once LAN Only Liveview is on.
